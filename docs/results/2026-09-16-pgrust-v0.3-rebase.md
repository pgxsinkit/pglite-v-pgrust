## What 0.3 is

One commit. `79ad992ede` — "v0.3: Try us on real world workloads in non-critical environments",
Michael Malis, 2026-09-15 — is a **root commit with no parents**: upstream republishes the whole
repository as a single squashed commit per release, so there is no history to rebase against and no
per-change attribution to read. What it carries, from this side of the fence:

| | v0.2 line (`dab0f92940` base) | v0.3 (`79ad992ede`) |
| --- | --- | --- |
| PostgreSQL | 18.3 | **18.6** |
| `version()` | `pgrust 0.2 (PostgreSQL 18.3 compatible) …` | `PostgreSQL 18.6 (pgrust 0.3) …` |
| `exprType` `T_NullIfExpr` | not ported | **ported** (`malisper/pgrust#109`) |
| `aclchk` compressed/external ACL | detoast gap | **detoasts** (`malisper/pgrust#110`) |
| child thread stack, `max_stack_depth=2048` | 4 MiB on wasm (our patch) | **16 MiB** — the scaled guard budget dominates the floor |

## The rebase

Twenty `spike(…)` commits moved across, in order, `6a7e4e0621 … 5eb87502c3`. **Eight files
conflicted** and every one was resolved by re-applying the spike's change onto 0.3's shape rather
than by keeping ours. One commit was **dropped**: `dab0f92940 perf(parser): borrow the source text
in parse analysis instead of copying it` — our own commit on the old base, and not carried forward,
because 0.3 rewrote what it patched.

The old line is not gone: `archive/spike-on-v0.2` = `46cb91c6cd` is the tip every number in the
three notes above was measured on, and it is pushed alongside the spike branch so those notes stay
reproducible.

## 3. Store continuity across the engine bump

Never a requirement, asked once because the answer is cheap and the alternative is finding out later.
A file-port store was built under bun with the **0.2** assets from release `pgrust-assets/e8e8ee06`,
filled with one table of 500 rows, `CHECKPOINT`ed and closed cleanly; the **same directory** was then
opened with the 0.3 assets:

```
[write] engine: pgrust 0.2 (PostgreSQL 18.3 compatible) on wasm32-wasip1-threads, 64-bit
[write] rows: 500
[read]  engine: PostgreSQL 18.6 (pgrust 0.3) on wasm32-wasip1-threads, 64-bit
[read]  rows: 500
```

**It opened and read.** No complaint at boot, none at first query, and the last row's payload came
back byte-identical. That is one minor-version step inside PostgreSQL 18 with the same catalog
version (`PG_18_202506291`), so it is the easy case rather than a promise about the next one — but it
does mean the bump did not silently strand a store. The two-leg script was scratch under
`tmp/agents/` and is not part of the repo; it used `createPgrustPglite` and nothing else.

## 4. Memory: 656.9 MiB → 263.5 MiB

The controlled single-column Chromium Speedtest from `2026-09-08-webkit-memory-diet.md` §3, rerun as
an A/B **on one machine in one sitting**: the same `dist/`, the same packed image (the two builds'
`vfs.img` are byte-identical), the same URL, and the module the only difference.

```
?configurations=pgrust-postmaster-opfs-repacked-relaxed&postmasterTuning=pool:8,max_stack_depth=2048
```

The metric is the Engine's own `WebAssembly.Memory.buffer.byteLength` at the end of the Run, read off
`data-testid=engine-stats-speedtest` — an allocation high-water, not a residency.

| Module | wasm memory | Suite total | Note |
| --- | --- | --- | --- |
| 0.2 `e8e8ee06`, 46 431 092 bytes | 688 848 896 B = **656.9 MiB** | 49 351 ms | the §3 number, reproduced exactly |
| 0.3 `5eb87502c3`, 53 414 445 bytes | 276 365 312 B = **263.6 MiB** | 47 970 ms | |
| 0.3, first run | 276 299 776 B = **263.5 MiB** | 97 737 ms | timing discarded: an unrelated build had the box |

The A arm landing on 688 848 896 bytes — the same byte count `m-B-msd2048-pool8` recorded eight days
ago — is what makes the B arm worth believing. **0.3 claims 393 MiB less for the same Suite**, and
the Speedtest's growth past the 256 MiB initial claim has all but stopped: 7.6 MiB, where 0.2 grew
401 MiB. The cells are within 3% of each other, so nothing was traded for it.

This is the **opposite** of what the rebase predicted, which is the interesting part. See below.

## 5. The open item: the stack diet is neutralised, and it did not matter here

The diet's third change — `child_thread_stack_size()`'s unlimited-reserve floor lowered from 16 MiB
to 4 MiB on wasm, worth −84 MiB on its own — rebased cleanly and then stopped doing anything. On 0.3
the reservation is no longer the floor: it is a **scaled guard budget**,

```
max_stack_depth x STACK_DEPTH_SCALE + 8 MiB     # 2 MiB x 4 + 8 MiB = 16 MiB
```

and `UNLIMITED_STACK_RESERVE` is only a `max()` under it. At the tuning this repo ships
(`max_stack_depth=2048`) the formula returns 16 MiB, the 4 MiB wasm floor never binds, and every
child thread reserves what it reserved before the diet — the nine threads of this lane's pool at
+12 MiB each, which is why an increase was expected.

The measurement says the peak fell by 393 MiB anyway: whatever grew 0.2's guest heap by 401 MiB over
the Speedtest is gone in 0.3, and the stacks are now absorbed inside a claim the Suite barely grows
past. So the patch is currently buying nothing, and the honest reading is that it wants re-deriving
against the new formula — lowering the 8 MiB slop, or the scale, is a different argument from
lowering a floor — rather than being carried verbatim. A separate bite, and not urgent at 263.5 MiB.

Two other things this note does not answer: the module's 15% growth, and whether the phone's memory
ceiling moved — `2026-09-08-webkit-memory-diet.md` §8 lists what a Chromium allocation number does
not say about iOS, and all of it still applies.
