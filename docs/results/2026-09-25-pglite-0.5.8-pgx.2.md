## What this answers

The bench's PGlite moved from the fork's `0.5.5-pgx.3` to `0.5.8-pgx.2`, which is upstream PGlite
0.5.8 under the fork's changes, the newest of them failing the instance on an engine exception
instead of swallowing it. The pre-release store bundle the pgrust broker columns load moved to
pgxsinkit `f4777b4`, which carries the store's half of the same fix: it poisons itself on a failed
platform write and reports it coded `EIO`. This note records what moved, which columns each change
reaches, and what it does to the numbers the recent notes lean on.

**Five findings.**

1. **The fixed store reached the five pgrust broker columns and not the two PGlite OPFS columns.**
   Those run the published `@pgxsinkit/pglite-opfs-repacked`, and `0.3.0` is still the newest on npm;
   the fix is in no published version. `0.3.0` also declares its PGlite peer as
   `>=0.5.5-pgx.0 <0.5.5`, which `0.5.8-pgx.2` is outside; it runs on it without a failure here (§1,
   §6).
2. **Against the earlier notes' Runs, the PGlite columns' Speedtest totals fall 11% and pgrust's
   1.2%.** PGlite Memory goes from 7 987–8 336 ms to 7 195–7 198, PGlite OPFS from 8 406–9 371 to
   7 758–7 774, pgrust from 11 607–12 802 to 11 890–11 932, so pgrust goes from 1.45–1.58× PGlite
   Memory to 1.65–1.66× and from 1.35–1.43× PGlite OPFS to 1.53×. The Prepared Suite's totals fall
   11.5–12.4% for PGlite and 14.7% for pgrust (§2).
3. **That is not the engine.** The old build and the new one, interleaved on the same box, put every
   Suite total within 4%: the Speedtest −2.0%, +1.3% and +0.8% (PGlite Memory, PGlite OPFS, pgrust),
   the Prepared Suite −0.0%, −0.2% and −1.8%, the RTT Suite's sum +3.8%, +2.6% and −1.1%. The old
   build itself ran the Speedtest and the Prepared Suite 12–15% faster there than in the Prepared
   Suite note's Runs of the same build, on every column (§3).
4. **pgrust's column does not move beyond noise.** Within 2% on the Speedtest, Prepared and RTT
   totals in the A/B. The Concurrency Suite's pgrust figures spread widely in both arms (writers on
   disjoint rows: old 3 992–5 108 transactions/s, new 2 951–4 936, the gate's new Runs 5 079–5 153),
   and the store's change touches only its failure paths (§1, §3).
5. **Memory does not move.** PGlite's emscripten heap ends every Speedtest Run at 226.3 MiB and every
   other Suite at 188.6, the same byte counts `0.5.5-pgx.3` reached in the store-levers note. pgrust's
   shared memory is 266.6–266.7 MiB on the Speedtest, 256.0 on RTT and Prepared and 270.2 on
   Concurrency, against 266.6, 256.0 and 270.0 there (§4).

| pgrust modules, host JS, `vfs.img` | threads `556d0731…`, single-session `4c010907…`, host `6ed7984bf0` | unchanged, byte for byte | |

- **The engine still reports PostgreSQL 18.3.** The environment line names the package, not the
  server, so the version above comes from `tmp/agents/pglite-bump/pgversion.ts` against each
  installed package under bun.
- **What the fork changed between the two** (pgxsinkit's `docs/runbooks/pglite-fork-override.md`):
  `0.5.5-pgx.4` initialises a live query's `refresh` before it can be called; `0.5.5-pgx.5` quotes the
  key column in the live incremental-diff joins; `0.5.8-pgx.1` rebases the stack onto upstream 0.5.8,
  whose engine reports its exit status through `_pgl_setPGliteExitStatus` instead of the
  `process.exitCode` save-and-restore, and brings upstream's `convert_to` fix and
  `PGlite.create(undefined, options)`; `0.5.8-pgx.2` rejects a statement whose engine call throws
  anything but Emscripten's own unwind, poisons the instance so every later statement throws the same,
  and maps an uncoded filesystem error to `EIO`.
- **What the store changed** (`2d6ea0d`, the only store source between `06ba369` and `f4777b4`): an
  arena write the platform rejected before confirming a byte, and a failed metadata-log append, now
  poison the store and throw `StoreFailedError`, which now carries `code` 29 (`EIO`). Two files,
  `repacked-vfs.ts` and `errors.ts`, and no path a successful write takes. The bundle is the package's
  whole entry, so it also carries the PGlite JS the package's factory imports: `0.5.8-pgx.1` in the
  old, `0.5.8-pgx.2` in the new.
- **How the bundle was made.** `bun run build:public-packages` in a clone of the pgxsinkit checkout at
  `f4777b4`, byte-identical to the checkout's own build (`7e912a53…`), then `bun run sync:pgrust` with
  `PGXSINKIT_DIR` pointing at the clone. `src/vendor/pgrust/SOURCE.md`'s store block names `f4777b4`
  and 1 010 981 bytes; the sync re-copied the modules, the host JS, `vfs.img` and `vfs.json` from the
  pgrust checkout at `6ed7984bf0`, byte-identical, and moved only the two timestamps in the other two
  blocks. The old bundle was rebuilt the same way at `06ba369` for §3 and came out byte-identical to
  the one it replaced (`6c8d8585…`).
- **Why the PGlite OPFS columns do not have the fix.** pgxsinkit publishes to npm from semver tags;
  `f4777b4` is on `develop`, and `0.3.0` (2026-08-24) is the newest release. The bench installs from
  public npm only.
- **The published store's peer range.** `0.3.0` declares `@electric-sql/pglite` as
  `>=0.5.5-pgx.0 <0.5.5`, which admits `0.5.5-pgx.3` and not `0.5.8-pgx.2`. `bun install` says nothing
  about it, and the e2e lane (§6), all eight gate Runs and the new arm's Runs of §3 ran both PGlite OPFS
  columns on `0.5.8-pgx.2` without a failure.

## 7. What this changes about earlier numbers

**Every earlier note's PGlite figures are on `0.5.5-pgx.3`**, from 2026-09-07 on; the 2026-08-29 and
2026-09-06 runs are on `0.5.5-pgx.2`. From this note on, the PGlite columns are on `0.5.8-pgx.2` and
the broker columns on the store at `f4777b4`. Beside `0.5.5-pgx.3` on one box the new build gives the
same totals within 4% (§3), so a ratio from an earlier note stays comparable. An earlier note's
absolute milliseconds do not: the same build ran 12–15% faster in this note's A/B than in the
Prepared Suite note's Runs of the same day (§3), and §2's before/after mixes that with the engine. No
older note was changed.

## Verdict

| question | answer | evidence |
| --- | --- | --- |
| What moved? | PGlite `0.5.5-pgx.3` → `0.5.8-pgx.2` (upstream 0.5.8, PostgreSQL 18.3 both), and the broker columns' store bundle `06ba369` → `f4777b4`. pgrust's modules and host JS did not move. | §1 |
| Which columns got the store fix? | The five `pre-release store` columns. Not the two PGlite OPFS columns: their store is the published `0.3.0`, and no published version has the fix. | §1 |
| Did the PGlite columns move? | Not on the same box: Suite totals within 4%. Against the earlier notes they are 11–12% lower, and the old build is 12–15% lower too. | §2, §3 |
| Did pgrust's column move? | Not beyond noise: within 2% on the Speedtest, Prepared and RTT totals; Concurrency spreads widely in both arms. | §3 |
| Memory? | Unchanged: PGlite 226.3 / 188.6 MiB, pgrust 256.0–270.2 MiB. | §4 |

## What this does not show

- **The fix itself.** Nothing here makes a platform write fail. The crash-and-reopen evidence is
  pgxsinkit's (`7d1ea5f`, `2d6ea0d`) and the fork's; this note measures only what the new builds cost
  on the path that does not fail.
- **The fixed store under PGlite.** The PGlite OPFS columns still run `0.3.0`, and `0.5.8-pgx.2`
  without the store half of the fix is what they measure.
- **Row-level effects of the engine under ~10%.** Two Runs per arm on a shared box; §3's single-row
  differences (PGlite Memory's row 7, the Warm-up) are not resolved.
- **Why the machine was 12–15% faster in the A/B than in the earlier notes' Runs**, or why two busy
  cores beside it slow pgrust's column more than PGlite's. Neither was traced.
- **Other columns under the gate, other browsers.** The eleven other columns ran once, in the e2e
  lane, ungated; Chromium only.
