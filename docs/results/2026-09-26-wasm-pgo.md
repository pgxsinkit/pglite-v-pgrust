## What this answers

[malisper/pgrust#117](https://github.com/malisper/pgrust/issues/117)'s native diagnosis found that
pgrust's extra cost per statement is mostly instructions per cycle rather than extra instructions,
and that a profile-guided build (pgrust `pgo/pgo-build.sh`, trained on `pgo/train.sql`) removes all
of it natively: rows 7, 9 and 1 from about 2× C PostgreSQL to 0.70–0.96× C, 20–23% fewer
instructions, half the calls. The owner asked for the fix module on the issue. A native profile
cannot steer the wasm build — LLVM finds a function's counts by its symbol name, and the wasm build's
names carry other crate hashes — so this collects a profile from the wasm build itself, builds the
threads module with it, measures it against the published one, and gates it.

**Four findings.**

1. **The browser Speedtest total falls 16%.** Three interleaved rounds per arm: 9 683–9 886 ms
   against 11 470–11 863 ms for the published module, rounds apart, the PGlite OPFS control flat
   beside both (8 271–8 465 ms). Every row but DROP TABLE is faster, 0.72–0.96×; rows 7 and 9 are
   0.83× and 0.82×. pgrust moves from 1.36–1.43× PGlite OPFS to 1.15–1.19× in the same Runs.
2. **The node lane's warm statement rows are 0.79–0.89×** — rows 7, 9, 1 at 0.89×, 0.84×, 0.79× of
   the published module, six interleaved processes per arm. That is a fraction of the native effect
   (0.36–0.54× there): the profile's inlining and code choices reach the wasm, but V8 does its own
   block layout and register allocation, which is where much of the native gain lived (the
   diagnosis's §12.4 said to expect this).
3. **The Warm-up line gets slower: 766–860 ms against 616–646 ms** (1.35× on the medians), the one
   line outside every Suite total, and in every Suite (Prepared 1.23×, RTT 1.20×, Concurrency 1.11×,
   one Run each). The module has 3 619 more functions with bodies (37 186 against 33 567) in 236 648
   fewer bytes of code; why V8 takes longer over it was not investigated.
4. **The profile is generic and it does not matter much which workload trains it.** The shipped
   profile is `pgo/train.sql` — no Speedtest text. A second profile trained on the Speedtest's own 18
   scripts gives a module within 1.5% of it on the Suite (median 9 683 against 9 830 ms, ranges
   overlapping), and within 3% on the node rows. The native note found the same (within 3%).

## 1. What was built, and what broke on the way

`PGRUST_WASM_PGO=generate` builds an instrumented `wasm32-wasip1-threads` module with the release
settings exactly (fat LTO, `opt-level 3`, one codegen unit, `browser` features) and no Binaryen pass;
`PGRUST_WASM_PGO=use:<profile>` rebuilds with `-Cprofile-use` and runs the usual
`wasm-opt -Oz --one-caller-inline-max-function-size=0`. Both legs reach our crates and their
crates.io dependencies through a `RUSTC_WRAPPER` and never the `-Zbuild-std` units, and each builds
into a target directory of its own. What broke, in the order it came up:

| # | What broke | Why | What fixed it |
| --- | --- | --- | --- |
| 1 | No profile runtime to link | `-Cprofile-generate` needs compiler-rt's `lib/profile` (`profiler_builtins`); the stock wasm targets do not ship it and `rust-src` carries no compiler-rt source; no clang on the box could target wasm | wasi-sdk 34 installed by the owner (clang 23.1.0 and the `wasm32-wasip1-threads` sysroot); compiler-rt source from the nightly's own LLVM (rust-lang/llvm-project `52ed14fc`, LLVM 22.1.8) as a sparse checkout; `profiler_builtins` in `-Zbuild-std`, built as upstream builds it for WASI (`-D_WASI_EMULATED_MMAN -D_WASI_EMULATED_GETPID`, the two emulation archives, `-pthread -matomics -mbulk-memory`) |
| 2 | `core` fails with `E0463 can't find crate for profiler_builtins` and 6 292 errors | rustc makes every instrumented crate depend on `profiler_builtins`, with no exception for `core`, and `profiler_builtins` depends on `core` | the wrapper leaves every build-std unit uninstrumented — as the native recipe's prebuilt std is |
| 3 | The instrumented module trained to a clean `exit(0)` and wrote nothing | after fat LTO nothing roots the hook LLVM plants to keep the runtime, so wasm-ld extracts the runtime and then garbage-collects it, `atexit` registration and all (a small crate: written without LTO, not with `lto = "fat"`) | `--export=__llvm_profile_runtime` on the instrumented link (`--undefined=` does not root it); the leg checks the module for the runtime |
| 4 | The first use build found no profile for 62 956 functions | cargo hashes a crate over its whole dependency graph, and the `-Zbuild-std` set (with `profiler_builtins`) is in it: every symbol name differed | both legs build with the same `-Zbuild-std` set; the use leg builds the runtime, never links it, and checks |
| 5 | A unit built under one set of wrapper flags looks fresh under another | cargo cannot see the wrapper's flags | a directory per leg (per profile for the use leg) that remembers its flags and is emptied when they change |

`-Cprofile-generate`, `panic=unwind` over wasm exception handling, and `-Zbuild-std` otherwise
coexisted without a complaint. pgrust `wasm/BUILD-PROFILES.md` has the detail.

**The dump.** The runtime writes its `.profraw` from the guest's own `exit(0)`, through the guest's
WASI calls, to `$LLVM_PROFILE_FILE`; no host code calls into the module. The postmaster lane exits
cleanly: the engine's `shutdown()` closes the host-pipes listener, Postgres takes that as a fast
shutdown, checkpoints, and `main` turns the `ProcExitThread` unwind into `std::process::exit`, which
is libc's `exit` and runs the handlers. The counters live in the one shared memory, so the dump the
postmaster's thread writes carries what the backend threads counted: `exec_simple_query`'s entry
block reads 51 566 after 51 556 training statements sent to a backend.

**Training.** `tmp/agents/pgo-wasm/train.ts` boots the instrumented module through
`createPgrustPglite` (the postmaster, backends as `node:worker_threads` guest threads, the broker
store, `relaxed` durability: `synchronous_commit=off`, `fsync=off`, as the browser's relaxed
columns and the native recipe), with `LLVM_PROFILE_FILE=/pgo/train.profraw` in the guest
environment. It runs pgrust's `pgo/train.sql` the way psql runs it: every plain statement its own
simple query, and every `\gexec` line's SELECT run and each cell of its result sent as its own simple
query. Under `--fs broker` every guest path is in the store, so the file lands there; the store is
on the engine's `file` port rather than the memory port, because a memory store is gone once
`close()` stops the storage worker and there is no hook between the guest's exit and that stop.
After `close()` the lane opens the store directory again with the same repacked library and reads
the file out. The guest's code path is the same on either port. The instrumented module ran the
51 556 statements in 24.6 s; the Speedtest profile's lane ran the 18 scripts (119 244 statements)
in 16.1 s.

## 5. What this does and does not show

- **One machine, one browser.** An i7-1165G7 with turbo off, headless Chromium 149 on Linux. No
  Safari, no Firefox, no phone. V8 recompiles the module its own way, and another engine's tiering
  may keep more or less of the profile's effect, and may price the Warm-up differently.
- **Two columns.** `pgrust-postmaster-opfs-repacked-relaxed` against `pglite-opfs-repacked-relaxed`.
  The other pgrust columns run the same threads module and were not measured; the single-session
  `postgres.wasm` (`pgrust Memory`, `pgrust OPFS`) is **not** profile-guided — untrained and
  unchanged — and the generate leg has never been run on that target.
- **Three rounds, and one Run of everything else.** Enough to separate the Suite totals by nearly
  five times the larger arm's own round-to-round spread; not enough to say anything per RTT test, and only the direction of the
  Prepared, Concurrency and memory figures.
- **Why the Warm-up is slower** was not investigated. The PGO module has 10.8% more functions and
  0.7% less code; whether V8 spends the difference compiling, and whether it recurs after a reload
  with a warm code cache, is not measured here.
- **The profile is one workload's.** Generic small OLTP statements; 13.7% of the module's functions
  ever ran under it. Paths it never reaches (DDL beyond CREATE INDEX, large sorts and spills, the
  extensions, replication) are compiled as cold as the profile makes them, and a workload that lives
  there could get slower. Nothing here measures such a workload.
- **The profile ages.** It matches this source exactly (no hash mismatch). As the engine changes
  under it, functions lose their counts and fall back to unguided codegen; the use leg's "no profile
  data" count says how far, and re-training is the generate leg, `pgo/train.sql` and the dump above.
- **Native is not the ceiling here.** The native build gets 1.9–2.8× on these rows; the wasm build
  gets 1.1–1.3×. How much of the rest is V8's own codegen and how much is left in the Rust was not
  separated.
